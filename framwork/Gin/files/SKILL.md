# 反馈自动处理

使用本技能处理技术反馈时，先收集证据，再判断归属，不要直接从现象跳到根因。归属只分为三类：前端、服务、未知。接口契约、数据配置、基础设施等只作为证据或排查方向记录，不作为独立分类。

## 处理流程

1. 提取反馈字段。
2. 基于证据判断问题属于前端、服务还是未知。
3. 检索知识库或历史问题。
4. 当服务不能排除时，查询服务日志和 KAE 链路。
5. 综合分析根因和置信度。
6. 仅在证据指向代码或置信度较低时，进行代码定位和源码分析。
7. 涉及生产影响或低置信度结论时，先人工确认。
8. 输出结构化排查报告。
9. 可选写入知识库或反馈池沉淀。

## Step 1：提取反馈信息

提取以下字段。只追问会阻塞下一步排查的缺失字段。

必填：

- `user_id` 或其他用户/账号标识
- `version` 或版本、构建号、环境
- `title` 问题标题
- `description` 问题描述

建议补充：

- OS、浏览器、客户端类型、App 版本
- 严重程度和影响范围
- 复现步骤
- 期望行为和实际行为
- 发生时间窗口，需包含时区
- 截图/录屏中的关键信息、控制台错误、Network 状态、API 路径
- `request_id`、`trace_id`、`instance_id`、`project_id`、租户/组织 ID。处理服务反馈时，`request_id` 是优先级最高的定位参数。
- 仓库地址、文件路径、错误堆栈、函数名

提取后，用一句话总结反馈概要；如果概要足以继续排查，就继续推进。

## Step 2：判断前端、服务还是未知

必须基于可观察证据判断，不要只凭语义猜测。

| 证据 | 归属 |
| --- | --- |
| 没有发出请求、点击无响应、控制台 JS 报错、路由/状态/UI 渲染异常 | 前端 |
| 请求已发出但返回 4xx/5xx、业务错误码、超时、响应体异常 | 服务 |
| 请求参数缺失或错误、响应字段变更、前后端字段约定不一致 | 未知，记录为接口契约线索 |
| 仅单个用户、租户、文件、数据对象异常 | 未知，记录为数据/配置/权限线索 |
| Pod 重启、OOM、依赖异常、慢查询、高延迟 | 服务 |
| 仅特定浏览器、OS、设备异常 | 前端 |
| 现象描述不足，既没有前端证据也没有服务端证据 | 未知 |

记录：

- 归属分类：前端 / 服务 / 未知
- 支撑证据
- 缺失证据
- 置信度，范围 0 到 1

如果分类为服务或未知，除非完全没有日志访问条件，否则继续执行 Step 4。若分类为前端但 Network 中存在异常接口，也要继续执行 Step 4 验证服务端。

## Step 2.5：收集前端证据

当前端问题不能排除时，优先通过以下渠道收集证据：

1. Console：检查 JS 报错、资源加载失败、CORS、CSP、前端框架运行时错误。
2. Network：检查是否发请求、URL/method/headers/body 是否正确、状态码、响应体、耗时、timeout/cancelled。
3. 前端异常监控：检查错误信息、堆栈、sourcemap、版本、浏览器、影响用户范围。
4. 埋点/用户行为日志：检查点击、路由跳转、关键事件、异常事件、用户操作路径。
5. 截图/录屏：检查交互状态、遮挡、disabled、loading、页面展示异常。
6. 本地或测试环境复现：确认是否稳定复现，以及是否与账号、权限、数据、浏览器、版本有关。

如果缺少 Console、Network、前端异常监控或复现证据，不要直接判定为前端；应先归为未知，并说明缺少哪些前端证据。

## Step 3：检索知识库

在可用知识源中搜索类似历史问题。内部工具只作为适配器，不作为硬依赖。

优先适配：

- `ai-docs recall` 或同类语义检索
- 问题单、事故记录、复盘、历史排查文档、本地文档、用户提供的历史记录

如果没有可用知识库工具，继续流程，并在报告中标注“未检索历史记录”。

记录：

- 使用的检索词
- 命中的相似记录和相似度
- 可复用的解决方案或注意事项

## Step 4：查询服务日志和 KAE 链路

当需要查询 KAE 或服务端日志时，先读取 `references/kae-srecli.md`，再给出具体 srecli 命令。

处理服务反馈时，优先索取并使用 `request_id`。它通常是定位单次请求最准确的参数。

按以下优先级查询：

- `request_id`
- `trace_id`
- `instance_id` + `project_id`
- API 路径 + 时间窗口
- `user_id` 或租户/组织 ID + 时间窗口
- 错误码或异常栈特征

如果没有日志权限或工具不可用，向用户优先索取 `request_id`，其次是时间窗口、`project_id`、`instance_id`、`trace_id`、API 路径或日志片段。不要中断整体流程；降低置信度并标注证据缺口。

日志结论格式：

```markdown
## 服务端日志查询结果
- 查询方式：
- 项目/实例：
- 时间窗口：
- 是否命中相关请求：
- 状态码/错误码：
- request_id：
- trace_id：
- 相关服务：
- 异常或事件摘要：
- 初步结论：
```

## Step 5：综合分析

结合反馈内容、归属判断、知识库结果、日志证据和代码线索，输出分析结论。

格式：

```markdown
## 分析结论
- 问题归属：
- 可能根因：
- 置信度：
- 影响范围：
- 支撑证据：
- 缺失证据：

## 排查建议
1. ...

## 修复建议
1. ...
```

置信度参考：

- `>= 0.8`：有日志、复现、代码或历史问题等强证据
- `0.6-0.79`：有部分证据，结论较可信
- `< 0.6`：证据不足，优先补充日志、复现或代码线索

## Step 6：代码定位与源码分析

满足以下任一条件时再分析源码：

- Step 5 置信度低于 `0.6`
- 日志或堆栈指向具体文件/函数
- 归属判断指向实现问题
- 用户明确要求代码分析

代码定位前，先从日志和反馈中提取线索：

- 错误堆栈：提取文件路径、函数名、行号。
- 错误码：在仓库中搜索错误码、错误文案、枚举定义。
- API 路径：定位路由定义、Controller、Handler、Service 实现。
- trace/request 日志：定位调用链中的入口服务和异常服务。
- 版本号或发布时间：检查相关时间窗口内的最近变更。

如需使用 GitLab、srecli 代码搜索或 GitLab API，先读取 `references/gitlab-code-search.md`。

认证要求：

- Cookie 有效期有限，不建议作为生产环境长期方案。
- 生产环境优先使用 API Token 或 OAuth 认证。
- 不要在报告中输出 token、cookie、session 或其他凭证。

代码查询优先级：

1. 使用 srecli Skill 内置的 GitLab 代码搜索能力。
2. 在 Cursor / AI IDE 中克隆目标仓库到本地后搜索。
3. 使用 GitLab API 或 GitLab MCP Server 查询代码、commit 历史和分支差异。
4. 如果以上不可用，使用用户提供的代码片段或请求相关文件。

重点检查：

- 错误处理缺失
- 空值、空数组、权限、边界条件
- 前端事件绑定、状态、路由问题
- 请求参数或响应字段契约不一致
- 超时、重试、幂等问题
- 并发、资源泄漏
- 配置、环境、灰度差异

结合代码实现输出辅助根因定位结论：

- 相关文件、函数和行号
- 代码逻辑与日志/现象的对应关系
- 最近变更是否可能引入问题
- 根因假设和置信度
- 建议修复方向

不要泄露密钥、凭证或大段私有代码。

## Step 7：人工确认

在最终报告或生产影响建议前，如果出现以下情况，先展示当前结论并请求用户确认：

- 置信度低于 `0.8`
- 无法查询服务端日志
- 修复建议会影响行为、权限、数据或部署
- 涉及多个团队归属

如果用户否定当前方向，回到 Step 2 或 Step 5，结合新证据重新分析。

## Step 8：输出报告

输出 Markdown 报告：

```markdown
# 反馈排查报告

## 基本信息
| 字段 | 值 |
| --- | --- |
| 反馈 ID | |
| 用户 ID | |
| 版本/环境 | |
| 时间窗口 | |
| 处理人 | AI + 人工确认 |

## 问题摘要

## 前端/服务/未知归属判断

## 已收集证据

## 知识库检索

## 服务端日志 / KAE 链路

## 源码分析

## 根因判断

## 解决方案

## 影响评估

## 后续建议

## 置信度与证据缺口
```

通过内部 CLI 发布报告是可选增强。如果发布能力不可用，直接提供 Markdown 报告。

## Step 9：知识沉淀

当反馈池、多维表、数据库或知识库可用时，写入简洁可复用的记录：

- 标题
- 现象
- 问题归属
- 根因
- 证据
- 解决方案
- 严重程度/影响范围
- 关键词
- 相关服务、仓库、文件
- 日志 ID 或 trace ID
- 处理日期

如果没有写入工具，输出 Markdown 或 JSON，供人工沉淀。

## 工具依赖策略

将公司内部工具视为可选适配器：

| 能力 | 首选适配器 | 降级方案 |
| --- | --- | --- |
| 知识库检索 | ai-docs / 内部知识库 | 本地文档或用户提供历史记录 |
| 反馈记录写入 | kdocs / dbsheet | Markdown 或 JSON 记录 |
| 报告发布 | comate-cli | 本地/聊天内 Markdown 报告 |
| 代码检索 | srecli / GitLab API / GitLab MCP | Cursor/本地 `rg` 或代码片段 |
| KAE 日志 | srecli | 用户提供日志/trace ID |

不要因为内部 CLI 缺失就中断流程。必须说明跳过了什么、原因是什么，以及对置信度的影响。
